# RED1: quarantine, restore, delete

Tests are in `tests/codex/test_red1_quarantine.py`. They use harmless marker bytes, `tmp_path`, and the fixture's temporary `SENTINEL_HOME`. They were reviewed against the code but **not run** in this round.

## High — a live quarantine can lose its only copy

**Test:** `test_red1_live_quarantine_is_not_reconciled_as_a_crash` (inferred from code; test unrun). **Attacker:** an ordinary user holding the target's deletion through a hostile oplock or another long file operation; the service maintenance thread runs meanwhile. **Steps:** quarantine commits the blob and journal, then waits before `mark_delete`. After the 60-second grace, `reconcile` sees the still-present original with the same hash, deletes the record and blob, and closes the journal. The blocked action then deletes the original and returns a quarantine ID with no recoverable copy. The test holds `mark_delete` and uses `grace=-1` to simulate expiry without a minute-long wait. **Effect:** loss of the only copy and false quarantine success. **Lines:** `agent/sentinel/quarantine.py:38, 201-209, 258-272`; `agent/sentinel/service/backend.py:254-260`. **Fix:** distinguish a live action from a crashed one with a cross-process action lease or ownership protocol. Reconciliation must not settle a still-running action merely because its row is old; coordinate the final deletion and journal cleanup with the same ownership check.

## Medium — a same-byte replacement defeats crash recovery

**Test:** `test_red1_reconcile_distinguishes_a_same_hash_replacement` (inferred from code; test unrun). **Attacker:** an ordinary user who can recreate a file at the old name after a deletion, combined with a crash or database failure before the journal row is closed. **Steps:** the original is quarantined; an open journal row remains; the attacker writes a new file with the same bytes at the original path. `reconcile` checks only SHA-256, decides the deletion never ran, and removes the quarantined record and blob. **Effect:** the newly placed detected file stays at the old name while Sentinel loses its quarantine record and its retained copy. **Lines:** `agent/sentinel/quarantine.py:258-272`; `agent/sentinel/db.py:666-674`. **Fix:** record the original volume and file ID in the journal, and require that identity as well as the hash before treating a present path as the original. A different file at that name must not cause the blob to be discarded.

## Medium — failed record deletion leaves a missing quarantine item

**Test:** `test_red1_delete_keeps_blob_if_record_removal_fails` (inferred from code; test unrun). **Attacker:** full disk, database I/O failure, or crash at the delete boundary. **Steps:** an approved delete unlinks the `.qbin` first; removing its database row then fails. **Effect:** the user receives an error, the quarantine list still shows the item, and restore fails because the only copy is gone. **Lines:** `agent/sentinel/quarantine.py:362-364`; `agent/sentinel/db.py:629-634`. **Fix:** make deletion recoverable across the blob/row boundary. For example, commit a deletion intent, remove the blob, then finish the row with startup recovery; on a database failure before intent is durable, keep the blob.

## Medium — a download mark can be missed before quarantine opens the file

**Test:** `test_red1_zone_mark_added_between_read_and_open_is_preserved` (inferred from code; test unrun). **Attacker:** an ordinary user process editing its downloaded file's alternate data stream. **Steps:** `quarantine` reads `:Zone.Identifier` by path before opening and locking the file. The test writes the mark in that interval. Quarantine stores `zone_identifier=None`, removes the original, and restore returns a copy without the mark. **Effect:** Windows download provenance is lost on restore. **Lines:** `agent/sentinel/quarantine.py:116-128, 165-168, 201-203, 349-359`; `agent/sentinel/gate_v2/winfile.py:298-319`. **Fix:** read the stream from the same opened file handle after writers are excluded, before recording the quarantine item. Treat an unreadable or changing mark explicitly.

## Low — the service hides a known failed download-mark restore

**Test:** `test_red1_service_reports_lost_download_mark` (inferred from code; test unrun). **Attacker:** a failed alternate-stream write, such as a filesystem or storage failure, at restore time. **Steps:** `restore` returns `RestoredPath.zone_identifier_preserved=False`; `ProductBackend.execute_plan` returns only the restored name and autostart count. **Effect:** an approved restore is reported as successful without telling the user that the download mark was lost. **Lines:** `agent/sentinel/quarantine.py:342-359`; `agent/sentinel/service/backend.py:637-644`. **Fix:** include the preservation result in the service response and show a warning when it is false. The regression test checks the response field.

## Other probes

The inspected code already binds original-file deletion to open handles and checks the copied default-stream hash (`quarantine.py:131-155, 193-209`; `winfile.py:298-319`). `create_new` refuses overwrite and verifies the final restore path (`quarantine.py:281-303`; `winfile.py:321-339`), including a restored target that exists or is a directory. Existing tests exercise junction and symlink redirection, hard links into protected roots, a post-hash replacement, two in-process quarantine claims, full-copy failure, corrupted blobs, and ordinary Zone.Identifier restoration (`tests/test_m7_actions.py:36-239`; `tests/test_svc8.py:125-170`). I found no additional concrete exploit for 8.3 aliases, trailing dots/spaces, `\\?\` or UNC forms, other alternate data streams, or two in-process restores: the restore lock and exclusive create cover the last case (`quarantine.py:305-310`; `winfile.py:321-339`). This does not establish safety for two independent processes or every filesystem alias.
