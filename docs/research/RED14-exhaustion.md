# RED14: Resource exhaustion

All tests inject failures or use harmless files under `tmp_path`; none was run in this sandbox. The temporary `SENTINEL_HOME` fixture is active in each test.

## High — full disk moves a sound database aside

**Attacker model:** crash, power loss, or full disk at service startup. **Steps:** create a valid state database, then make the next SQLite open fail with `OperationalError("database or disk is full")`. `Database.__init__` treats every non-busy `DatabaseError` as corruption (`agent/sentinel/db.py:180-192`). `_rebuild` moves the original and sidecars before trying `_open` again (`agent/sentinel/db.py:216-245`). The service calls `Database` while building its backend (`agent/sentinel/service/backend.py:760-770`). **Effect:** the only live database path disappears, and a still-full disk prevents the replacement database from opening. The service cannot start; state is needlessly displaced. **Fix:** classify storage and I/O errors separately from confirmed corruption; leave the original and WAL untouched when the error is ENOSPC. Only rebuild after an integrity check establishes damage, and stage a replacement before switching names. **Evidence:** proven by `test_full_disk_at_database_open_preserves_existing_state` with an injected SQLite disk-full error.

## High — thread creation failure permanently removes scan capacity

**Attacker model:** a medium-integrity process drives handle/thread pressure, while hostile files hold scan operations. **Steps:** a running lane job exceeds its limit. `sweep` marks the old thread replaced and increments `stuck` (`agent/sentinel/service/backend.py:159-176`), then calls `_add` (`agent/sentinel/service/backend.py:177-178`). `_add` starts a thread with no failure recovery (`agent/sentinel/service/backend.py:125-126`). If `Thread.start` raises `RuntimeError`, later sweeps see the old thread in `replaced` and do not retry (`agent/sentinel/service/backend.py:166-173`). The watch loop only logs the exception (`agent/sentinel/service/backend.py:274-289`); status reports `realtime` from the action barrier and `stalled`, but not live lane capacity (`agent/sentinel/service/backend.py:346-362`). **Effect:** the observed lane can have no active worker while work remains queued; recovery depends on the stuck operation returning, which may never happen. **Fix:** track unfilled replacement slots and retry thread creation on later sweeps, or mark the lane unavailable and report the coverage gap. **Evidence:** proven by `test_failed_replacement_thread_is_retried` with a one-time synthetic thread-start failure. The end-to-end service outage is inferred from the lane and watch-loop control flow.

## Medium — large directory cursor replay ignores pass bounds

**Attacker model:** a downloaded file or user process creates a directory with very many entries; a journal gap triggers reconciliation. **Steps:** after a bounded pass saves a `last` entry, a restart reconstructs that frame (`agent/sentinel/service/reconcile.py:162-164`). `_open` scans from the beginning until it finds `last`, without consulting the deadline or `max_entries` (`agent/sentinel/service/reconcile.py:147-160`). The outer loop checks both only before `_open` (`agent/sentinel/service/reconcile.py:166-180`). **Effect:** replaying a cursor near the end of a million-entry directory can monopolize the observer's journal thread for an unbounded time. The loop catches and logs exceptions but has no timeout for this operation (`agent/sentinel/service/observers.py:329-342`). **Fix:** budget replay steps and elapsed time; persist replay progress or use a bounded restart strategy that does not skip unoffered entries. **Evidence:** proven by `test_directory_resume_obeys_reconciliation_budget` with 101 harmless entries and a synthetic clock; million-entry impact is inferred.

## Other required probes

* **Quarantine disk full:** `_copy_xor` writes and fsyncs before deleting originals (`agent/sentinel/quarantine.py:107-113,185-225`); a copy failure enters cleanup (`:225-238`). Existing `tests/codex/test_agent_edges.py:83-103` already tests partial-blob rollback. No distinct finding here.
* **Cursor writes:** `read_batch` reports `cursor_store_error` when its save raises `OSError`, returning resolved changes and a gap (`agent/sentinel/service/usn.py:247-253`); `Observers.tick_journal` offers these and marks reconciliation owed (`agent/sentinel/service/observers.py:247-262`). This is reported rather than silently clean.
* **Worker memory and input frames:** the worker is launched with a memory limit (`agent/sentinel/service/workerclient.py:92-99,115-128`), and IPC frames are bounded (`agent/sentinel/service/protocol.py:15-22,54-63`). A worker death becomes a non-clean failure (`agent/sentinel/service/workerclient.py:139-158,166-198`). No further proven finding.
* **Very many requests:** service IPC limits waiting jobs per caller and globally (`agent/sentinel/service/core.py:185-218`), while the observed lane has a 2,048-slot semaphore (`agent/sentinel/service/backend.py:201-207,423-429`). ETW queues also have configured capacity (`agent/sentinel/service/etw.py:259-263`). These paths refuse or count excess work; the failed replacement above is the separate capacity gap.
* **Deep junctions:** the reconciliation walker skips reparse points and counts them, and caps stack depth (`agent/sentinel/service/reconcile.py:205-221`). No cycle or depth finding.
* **Logs:** the installed service uses a 5 MiB rotating file with three backups (`agent/sentinel/service/entry.py:63-67`); database events are pruned to 20,000 rows by maintenance (`agent/sentinel/db.py:157,602-608`; `agent/sentinel/service/backend.py:255-272`). A full disk can also break logging or maintenance, but the tested database path is the actionable failure above.
