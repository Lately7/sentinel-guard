# R14 — User-mode ransomware detection with ETW and canary files

## Verdict: build a reduced version

Build a **measured, canary-triggered suspension prototype** after the service and its owner-run administrator checks are working. Use file ETW to attribute a confirmed canary modification to an ordinary user process. Keep broad behavioural detection **notify-only** until it demonstrates a very low false-alarm rate on this PC.

A canary can give an early signal when a file-walking encryptor reaches it. It cannot guarantee that the first real file survives: ETW delivers events after the operation, file order varies, and a process can modify many files while an ETW buffer awaits delivery. The published “few files lost” results come largely from systems with kernel interception or file recovery; they cannot be transferred to Sentinel’s user-mode service. [CryptoDrop](https://www.cise.ufl.edu/~butler/pubs/icdcs16.pdf), [ShieldFS](https://blackhat.com/docs/us-17/wednesday/us-17-Continella-ShieldFS-The-Last-Word-In-Ransomware-Resilient-Filesystems-wp.pdf), [Redemption](https://kharraz.org/publications/raid2017redemption.pdf).

The repository already calls for ETW and canaries as a later experiment (`docs/ROADMAP.md:73-84`), chose a thin `ctypes` LocalSystem service and process snapshots before ETW (`docs/research/R13b-design-discussion.md:16-37,73-77`), and places content parsing in a restricted worker (`docs/research/R13b-design-discussion.md:55-71`). Today’s watcher debounces changed paths for 1.5 seconds, caps pending paths at 10,000, reports overflow, and has no writer PID (`agent/sentinel/watcher.py:26-40,55-75,96-117,142-152,214-240`). Its settled-file scanning must remain separate from this rapid-response path.

**Decision gate:** if the owner’s machine cannot deliver reliable file-to-process correlation with acceptable loss and latency, ship canary and change-burst **alerts only**. Do not suspend from a directory notification or USN record with a guessed writer.

## 2. ETW implementation decision

A `ctypes` consumer is **technically viable for a prototype**, especially for process events. Its viability for system-wide file I/O at a useful latency is **unproven**. Do not add a native helper merely from assumed event rates. First measure the service’s Python callback with a bounded no-I/O callback and a separate aggregation thread. If it loses events, raises service CPU beyond the agreed budget, or makes the service unresponsive under normal owner workloads, move the consumer and correlation table to a **small, audited native helper**; the privileged service should receive only bounded canary/candidate records. Python’s foreign-thread callback creates Python thread state and must retain the callback object; this is overhead and a crash hazard, not a published throughput limit. [Python `ctypes` callbacks](https://docs.python.org/3.12/library/ctypes.html).

**API sequence (proposed):**

1. On the owner’s Windows build, enumerate provider metadata with TDH or `wevtutil gp`; record provider GUID, event ID, version, keywords, and payload fields. Choose one private, versioned session name and GUID. Check active sessions; never attach blindly or stop a same-name session of unknown ownership.
2. Allocate one contiguous `EVENT_TRACE_PROPERTIES` buffer with room for UTF-16 session and log names. Set `Wnode.BufferSize`, `WNODE_FLAG_TRACED_GUID`, a fresh session GUID, QPC clock context, `EVENT_TRACE_REAL_TIME_MODE | EVENT_TRACE_SYSTEM_LOGGER_MODE` if using system providers, buffer size/min/max, and a **1-second flush timer for the latency experiment**. A full buffer can deliver sooner; one second is not a latency guarantee. Start with Microsoft’s moderate/high-rate buffer guidance, then tune from measurements. `StartTraceW`; on `ERROR_ALREADY_EXISTS` or `ERROR_NO_SYSTEM_RESOURCES`, record unavailable coverage. Do not change the OS logger limit. [Session setup](https://learn.microsoft.com/en-us/windows/win32/etw/configuring-and-starting-an-event-tracing-session), [properties and buffer advice](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/ns-evntrace-event_trace_properties), [64 usual total / eight system logger limit](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-starttracea).
3. `EnableTraceEx2` for the selected system IO/process providers and keywords; or, for a separately validated manifest-provider session, enable the manifest GUIDs and their keywords. Do not mix manifest IDs with classic FileIo types. Enable only measured necessary categories. A PID filter is not a suitable folder filter and may apply only to user-mode provider instances. [System providers](https://learn.microsoft.com/en-us/windows/win32/etw/system-providers), [PID-filter limits](https://learn.microsoft.com/en-us/windows/win32/api/evntprov/ns-evntprov-event_filter_descriptor).
4. Set `EVENT_TRACE_LOGFILEW.LoggerName`, `PROCESS_TRACE_MODE_REAL_TIME | PROCESS_TRACE_MODE_EVENT_RECORD`, and a retained `WINFUNCTYPE` `EventRecordCallback` (plus buffer callback). `OpenTraceW`, then run blocking `ProcessTrace` on a dedicated thread. Copy only a validated, bounded event header and the needed payload into a preallocated/bounded queue; never retain pointers into callback-owned memory, parse content, call the DB, or invoke suspension from this callback. Parse versioned payloads with TDH or verified layouts in the aggregation thread. [Consumer API](https://learn.microsoft.com/en-us/windows/win32/etw/consuming-events), [logfile modes](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/ns-evntrace-event_trace_logfilea).
5. Query `ControlTrace(EVENT_TRACE_CONTROL_QUERY)` at least every few seconds and after each burst. Persist deltas of `EventsLost`, `RealTimeBuffersLost`, and `LogBuffersLost`; also record application-queue drops, unmatched name/PID joins, callback lag, and longest delivery delay. ETW can deliver explicit lost-event/buffer indications. **Any nonzero loss makes the interval a coverage gap**; USN can discover changed paths later but cannot reconstruct a missing writer. [Properties](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/ns-evntrace-event_trace_properties), [lost-event classes](https://learn.microsoft.com/en-us/windows/win32/etw/rt-lostevent).
6. On orderly stop, disable owned providers, `ControlTrace(STOP)`, `CloseTrace`, join the consumer, and close handles. A crashed controller can leave its session running. On restart, query the private name, verify its stored GUID/ownership marker against protected service state, then stop **only Sentinel’s** orphan before starting another. Mark the downtime and possible buffered-event interval as a gap. [Session lifetime](https://learn.microsoft.com/en-us/windows/win32/etw/configuring-and-starting-an-event-tracing-session), [consumer shutdown](https://learn.microsoft.com/en-us/windows/win32/etw/consuming-events).

**Required measurement:** event/s, callback CPU, end-to-end p50/p95/p99 and maximum latency from a simulator’s timestamped operation to aggregation, trace-loss deltas, queue high-water mark, memory, and effect on normal desktop responsiveness. Collect idle, browsing, game update, OneDrive sync, backup, build, and install periods. No defensible “busy desktop events/s” figure was found that predicts this machine.

## 3. Canary design

**Hypothesis for the first deployment:** 12–24 small, valid, harmless documents on a single owner PC, roughly 2–4 per locally protected root (`Documents`, `Desktop`, `Pictures`, and any owner-chosen local work root), in ordinary subdirectories and at more than one depth. Mix valid `.txt`, `.csv`, `.docx`/`.pdf` and image formats where that type belongs. Names should look like ordinary personal files, with no “sentinel,” “canary,” hidden/system attribute, or obviously special prefix. Give them ordinary owner read/write ACLs; a read-only/DENY ACL would prevent the very write being measured and alter traversal. Store expected file ID, size, and cryptographic hash in the service-owned protected store; revalidate after startup and each relevant change. Never put a canary in a synced or backed-up root without first measuring the resulting noise. The `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED` bit can reduce content-indexer reads but may itself make a file unusual; prefer disregarding reads and testing indexer behaviour. These are placement hypotheses, not published optimal counts.

The detector needs a **confirmed change** to canary content, replacement, deletion, or rename plus a strongly attributed ordinary writer. An open/read, oplock break, timestamp-only modification, or cloud placeholder hydration is not enough. If a backup, synchronization, or restore tool changes a canary, record it as a benign case and adjust placement or the decision rule; do not create a signer-name allowlist.

Published studies show why one “alphabetically first” trap is weak. R-Locker reports differing folder and file traversal orders; Pepper trained placement preferences on 650 older samples, tested on 303 held-out samples, and reports 98.68% detection with mean 2.27 files lost across its evaluation. Its monitored user systems accessed decoys about 2.5 times per day, showing that **access alone is noisy**. These are study-specific outcomes, not a general evasion rate for Sentinel. I found no defensible published percentage for “ordinary encryptors that deliberately skip Sentinel’s canaries.” A file-walker that does not touch them is handled only by the slower burst detector, Defender/CFA, and backups. [R-Locker](https://ietresearch.onlinelibrary.wiley.com/doi/10.1049/ise2.12042), [Pepper](https://doi.org/10.1145/3728932).

| **Redemption** | Kernel interception diverts writes into reflected files while scoring cross-document access, content and write frequency; suspends and asks the user. **Computability without service content parsing:** ETW can support per-process counts of distinct named files, directories, read-before-write order, write sizes/offsets, create/rename/delete patterns, and approximate extension churn **where name and PID joins succeed**. USN and directory notifications can support per-root change/rename rates but not a writer. None supplies entropy, byte comparison, or trustworthy file-type change. Entropy requires **bytes from two comparable generations**; after-the-fact reading cannot recover overwritten originals. If Sentinel has a pre-change, bounded sample for a selected file, the service may open and pass a read-only duplicate handle to the existing restricted worker for hashing/type/entropy, subject to generation checks. The privileged process must not parse content: that placement is the R13b P4 decision (`docs/research/R13b-design-discussion.md:55-61`), and the worker launcher already creates a restricted, low-integrity, job-limited process (`agent/sentinel/service/worker.py:123-176,244-290`). Do not collect plaintext user-file samples merely to improve this detector without a separate privacy and storage decision.

**Proposed decision rule, all numbers hypotheses:**

- **Canary candidate:** one confirmed data/content or identity-changing canary operation, strongly joined to `(PID, creation time)`, with no ETW gap. Immediately verify canary identity/hash and process eligibility. Suspend only after the verification and **at least one corroborating** change to a different owner document within a proposed 10-second window, or after a second distinct canary changes. This sacrifices some speed to protect the false-alarm budget.
- **General burst:** proposed 8 distinct owner documents in 10 seconds across at least two directories, with read-then-write/replace and a common process identity. Initially **alert only**. Treat extensions, high write volume, or entropy as corroboration, never standalone proof.
- Freeze these thresholds before the evaluation period. Measure alert counts per **device-day**, per workload, and per process, plus files changed before decision. A desired gate might be **zero unwarranted suspensions across 30 owner-days including each listed workload**, but zero observed events provides only a limited statistical bound; it is not proof of zero future FPs. A single unjustified suspension rejects the automatic rule until reviewed.

**Benign lookalikes and discriminators to test:** 7-Zip and backup tools read many originals and usually write archives or backup destinations; test compression with “delete originals” and mirror/restore modes, where this distinction disappears. OneDrive can rewrite or rename synced files and hydrate placeholders; prefer local unsynced canaries and examine cloud process context without treating signer alone as trust. Game launchers, installers, git, package managers, and IDEs create/replace many files, usually within their installation, repository, package-cache, or build trees; a broad read-then-replace sweep of independent personal documents is more concerning, but user projects inside Documents defeat a simple path rule. Video encoders read many media inputs and write new output, sometimes replacing inputs; test batch and replace-original modes. BitLocker works below the file system and EFS changes encryption state at file-system level; neither should be inferred from ordinary high-entropy output files. A signed executable, name, parent process, or familiar path can contribute context but never exempts a process that modifies canaries and unrelated personal files. CryptoDrop observed 7-Zip as a benign FP, and Redemption explicitly observed legitimate encryption/secure deletion overlap. [CryptoDrop](https://www.cise.ufl.edu/~butler/pubs/icdcs16.pdf), [Redemption](https://kharraz.org/publications/raid2017redemption.pdf).

## 5. Response and safety

`NtSuspendProcess` offers one process-handle operation, requiring `PROCESS_SUSPEND_RESUME` (`0x0800`); it is an NT interface rather than a documented Win32 suspension contract. Enumerating threads and calling `SuspendThread` needs `THREAD_SUSPEND_RESUME` for every thread, races new thread creation, and can leave partial suspension. Microsoft describes thread suspension as debugger-oriented and unsuitable for synchronization. Neither action automatically suspends descendants or a whole job; separately acting on a tree raises attribution and race risks. [Process rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights), [thread suspension](https://learn.microsoft.com/en-us/windows/win32/procthread/suspending-thread-execution), [process-tree independence](https://learn.microsoft.com/en-us/windows/desktop/ProcThread/terminating-a-process).

**Implementation rule:** after obtaining a live handle and rechecking creation time/image, attempt `NtSuspendProcess` only for an eligible ordinary interactive process. Record NTSTATUS, start/end time, handle identity, and whether suspension was confirmed. Never suspend PID 0/4, Sentinel or its worker/tray, Windows system components or service hosts, protected/PPL processes, Defender or other security products, processes outside the owner’s interactive scope, or any target whose identity/protection status is uncertain. `OpenProcess` denial is an abstention, not a reason to enable `SeDebugPrivilege`. Protected process access is restricted by Windows; Sentinel must additionally apply its own conservative policy. [Protected-process rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights), [protection-level query](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_protection_level_information).

Show the unelevated tray a Vietnamese prompt with process image, verified file, modified canary/documents, confidence and gap status. The user can request resume or continued hold; bind the request to the exact process creation time and incident. R13b already requires elevated, plan-bound confirmation for security-weakening commands because malware under the same user SID can send pipe requests (`docs/research/R13b-design-discussion.md:39-53`). The service must own the deadline, not the tray. **Hypothesis:** hold at most 120 seconds without a response, then automatically resume and retain a prominent incident alert; never leave an ordinary application frozen indefinitely after a service/tray failure. This is a safety choice with a real protection cost: an unattended encryptor may continue. Measure prompt reachability and timeout outcomes before enabling automatic suspension. A service restart must reconcile a protected suspension journal and resume any Sentinel-owned, still-identical process by its deadline.

There is **no finite worst-case number of files lost** from ETW latency alone. If an encryptor can complete at most \(r\) files/second, \(N_{\text{before}}\) files precede the triggering canary/threshold, \(L\) is detection-to-suspension latency, and \(q\) files are already in flight or changed by children, then an engineering bound is approximately

\[
N_{\text{lost}}\ \leq\ N_{\text{before}}+\lceil rL\rceil+q
\]

only under those measured rate and concurrency bounds. Without them, or during an ETW gap, the bound is unbounded. The simulator should report the observed components separately, including the file whose write caused the alert.

A LocalSystem service can act as a VSS requester through VSS APIs, and may inspect available snapshots where permitted, but that would be a separate backup/recovery feature with storage and consistency design. This detector must **never delete or alter shadow copies**: deleting one permanently removes prior versions or restore points that may be the owner’s recovery path. No VSS state mutation belongs in the suspension response. [VSS requester role](https://learn.microsoft.com/en-us/windows/win32/vss/requestors), [VSS overview](https://learn.microsoft.com/en-us/windows-server/storage/file-server/volume-shadow-copy-service), [deletion consequence](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/vssadmin-delete-shadows).

## 6. Bounded state and degradation

Use a single incident state machine:

`DISABLED → OBSERVE → CANDIDATE → VERIFIED → SUSPEND_ATTEMPTED → HELD → RESUMED/CLOSED`.

From any active state, trace loss, queue overflow, missing name/PID join, process exit/reuse, denied handle, hash mismatch, unsupported volume, or collector failure moves the affected scope to `GAP/ABSTAIN`. `GAP` records start/end, reason, counters, and reconciliation debt. It does **not** silently reset to “protected”; returning to `OBSERVE` requires successful resubscription, fresh canary identities, and an explicit gap closure. USN/watchdog reconcile changed files, but the interval remains historically unattributed.

Proposed initial bounds, to tune by measured high-water marks: up to 256 canaries; 65,536 live `FileObject→name` entries with short TTL and close eviction; 16,384 `(PID, creation time)` process records; 4,096 active per-process rolling score records; 8,192 queued compact events with a reserved canary lane; 256 live candidates; 16 simultaneous prompts; fixed-size strings and payload copies; per-root counters and a fixed-size persistent incident record. Eviction, truncation, parse failure, and every dropped record must increment an explicit counter. A full priority lane cannot justify dropping canary evidence silently. On sustained loss, disable automatic suspension, retain notify-only canary verification, and display degraded coverage. These sizes are **implementation hypotheses**, not recommended Microsoft ETW settings.

## 7. Measurement without malware

Create a separately reviewed **benign simulator** that accepts only a disposable test directory created by the harness. It must reject a root, user profile root, junction/reparse traversal, network path, or directory outside its harness marker; create its own harmless corpus; and log a monotonic timestamp for each operation. Modes should include read→transform with a fixed test key→overwrite, write-new→rename→delete-old, partial writes, multiple workers, differing file orders, slow/fast rates, and an option to skip canaries. The key and outputs are test data, not malware. Restore the disposable directory from a clean seed between runs. Measure time to each event, decision, suspend call/confirmation, number of corpus files modified, canary rank, false negatives, gaps, CPU, and memory. No real malware or EICAR is necessary.

For FPs, capture **metadata-only** ETW/USN/directory traces for the owner’s consented benign workloads listed above, with process identity, operation, path category, timing, and lengths. Replay them through the same deterministic scoring engine and compare with live observe-only decisions. Metadata replay cannot supply before/after entropy, real kernel buffering, live PID races, or actual suspension side effects; those need benign live tests. The simulator also cannot show adaptive malware, tampering by an administrator, PPL behaviour, or prevalence in the wild. Preserve workload labels, detector version, threshold, and observation duration so an FP claim has a denominator. This follows the project’s existing low-FPR and temporal-evaluation direction (`docs/handoff/codex-literature-r7.md:173-203,238`).

The owner may enable it; Sentinel must only observe its status and never change Defender settings. |
| **Malwarebytes Ransomware Protection** | The Windows real-time layer says it detects and prevents malicious software from locking the user out. Its public consumer page does not publish thresholds or a file-loss guarantee. [Malwarebytes help](https://help.malwarebytes.com/hc/en-us/articles/31589448817563-Turn-on-Real-Time-Protection-in-Malwarebytes-for-Windows-and-Mac). [Feature description](https://www.bitdefender.com/consumer/support/answer/13349/), [exceptions](https://www.bitdefender.com/consumer/support/answer/16792/). | Sentinel has neither those protected copies nor their documented restoration workflow. |

Each has a specific owner-machine measurement above.
