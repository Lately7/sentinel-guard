# R17 — a file-event source for shadow ransomware scoring

Research only, 2026-11-03. No trace session or installed service was touched. **Inference** marks a project conclusion or a performance expectation rather than a documented Windows guarantee. The owner's reported system-logger trial lost **373,432 events in a few seconds**; the duration, generated-event count, and workload breakdown are not available here, so that number cannot be converted to a measured events/second rate.

## What the current code needs

`shadow.py` accepts process start/stop, file-object name, read, and write events. It holds names for 10 seconds, uses only paths under configured document roots with selected extensions, and reports `usable_io_share`, unmatched joins, gaps, and provisional alerts. It does **not** consume rename/delete, prove a write succeeded, or recheck a live process handle. `burst.py` can score read-before-change across 8 distinct documents in 2 directories within 10 seconds, but `shadow=True` deliberately treats those changes as provisional. Its verified-canary route needs confirmed change and strong attribution unavailable from this ETW path. **Inference:** more event kinds alone cannot make the current observer's suspension evidence trustworthy.

`etw.py` currently runs a private **system logger**, parses classic FileIo opcodes 0/32/35/36 and 67/68 (versions 2/3), and enables **process events only**. Its `set_file_events` can enable the System IO provider, but the owner trial led to disabling it. The callback copies at most 512 payload bytes into an 8,192-item queue; it counts ETW and queue loss and guards file traffic after a sustained 20,000 callbacks/s for 15 seconds. **Inference:** that guard cannot save the initial burst or make lost intervals complete. This is a different provider and schema from `Microsoft-Windows-Kernel-File`; the classic parser cannot be reused for manifest event IDs. `usn.py`/`observers.py` already provide a 5-second, close-only NTFS journal poll for later file discovery and reconciliation, with no writer identity.

## 1. `Microsoft-Windows-Kernel-File`

Provider GUID `{edd08927-9cc4-4e65-b970-c2560fb5c289}`. Microsoft's [PerfView parser](https://github.com/microsoft/perfview/blob/main/src/TraceEvent/Parsers/Microsoft-Windows-Kernel-File.cs) lists these keyword bits: `FILENAME=0x10`, `FILEIO=0x20`, `OPEND=0x40`, `CREATE=0x80`, `READ=0x100`, `WRITE=0x200`, `DELETEPATH=0x400`, `RENAMESETLINKPATH=0x800`, `CREATENEWFILE=0x1000`. Names and event layouts below come from Microsoft's [generated Tx manifest model](https://github.com/microsoft/Tx/blob/master/Generated/Microsoft_Windows_Kernel_File.cs), not from a capture on this Windows build. Verify with `wevtutil gp Microsoft-Windows-Kernel-File /ge:true` or TDH on the owner's build before coding offsets.

| Event ID (manifest, **not** classic opcode) | Payload relevant to scoring | Name in this event? |
|---|---|---|
| 10 NameCreate, 11 NameDelete | `FileKey`, `FileName`; `FILENAME` keyword | Yes, but **no `FileObject`**; these are name-map events, not file changes. |
| 12 Create | `Irp`, `FileObject`, issuing thread, create options/attributes/share access, `FileName`; `FILEIO` + `CREATE` | Yes; an open/create request does not prove a new file. |
| 15 Read, 16 Write | Byte offset, `Irp`, `FileObject`, `FileKey`, issuing thread ID, size and flags (`ExtraFlags` in v1); `FILEIO` + `READ`/`WRITE` | **No.** Requires a lifetime-safe name join. |
| 17 SetInformation, 18 SetDelete, 19 Rename | `Irp`, `FileObject`, `FileKey`, extra information, issuing thread, info class; `FILEIO` | **No.** `InfoClass`/status and name correlation matter; a request is not proof of final change. |
| 26 DeletePath, 27 RenamePath, 28 SetLinkPath | The above identity/info fields plus `FilePath`; respective `DELETEPATH` or `RENAMESETLINKPATH` keyword | Yes; path-bearing companions, not interchangeable with IDs 18/19. |
| 30 CreateNewFile | Create-like fields plus `FileName`; `CREATENEWFILE` keyword | Yes. |
| 24 OperationEnd | `Irp`, extra information, `Status`; `FILEIO` + `OPEND` | No; may correlate completion by `Irp`, with races and loss. |

The `EVENT_RECORD.EventHeader` has `ProcessId` and `ThreadId`; v1 operation payloads also include `IssuingThreadId`. [ETW event metadata](https://learn.microsoft.com/en-us/windows/win32/etw/event-metadata-overview) and the [Tx model](https://github.com/microsoft/Tx/blob/master/Generated/Microsoft_Windows_Kernel_File.cs) distinguish header metadata from payload. **Inference:** header PID is a candidate attribution, not a guaranteed original writer in cache/async/system contexts. A `FileObject` pointer may be reused; `FileKey` is not a PID. Confirm process creation time/image separately and measure joins. V0 and V1 offsets differ. `FileName`/`FilePath` filtering cannot directly select v1 read/write events because those events contain no path.

### Filtering before delivery

For a manifest provider, `EnableTraceEx2` can pass `ENABLE_TRACE_PARAMETERS` with `EVENT_FILTER_DESCRIPTOR` entries. Microsoft documents [keyword matching and up to 64 event IDs](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-enabletraceex2) and says an [event-ID filter](https://learn.microsoft.com/en-us/windows/win32/api/evntprov/ns-evntprov-event_filter_descriptor) is checked at each event write. An include list such as 10–19, 24, 26–28, 30 could suppress unrelated manifest events **before delivery**, if validated on this provider/build. It still admits every machine-wide read and write selected. Keyword masks can omit whole categories, but `FILEIO` occurs on many operations; verify the actual `MatchAnyKeyword`/`MatchAllKeyword` behavior with the installed manifest. Microsoft's [PerfView consumer](https://github.com/microsoft/perfview/blob/main/src/TraceEvent/Parsers/Microsoft-Windows-Kernel-File.cs) exposes the manifest provider and its Create event; [golang-etw's controller source](https://github.com/0xrawsec/golang-etw/blob/master/etw/provider.go) constructs an `EVENT_FILTER_TYPE_EVENT_ID` descriptor and even uses this provider in its syntax example. That is evidence of real controller practice, **not** a throughput result for this machine.

`EVENT_FILTER_TYPE_PID` has a maximum of eight **current** PIDs and is documented to enable user-mode provider instances only; when the same provider is registered in kernel mode, it is not enabled there. It cannot provide system-wide kernel file coverage, and process churn would break a fixed list. `EVENT_FILTER_TYPE_EXECUTABLE_NAME` is a scope filter associated with system-wide private logger configuration, not a documented way to select the actor of kernel FileIo events; it would also miss unknown processes. [Filter descriptor](https://learn.microsoft.com/en-us/windows/win32/api/evntprov/ns-evntprov-event_filter_descriptor), [EnableTraceEx2 limits](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-enabletraceex2).

`TdhCreatePayloadFilter` builds a filter for **one event descriptor** of a manifest provider, including string predicates such as case-insensitive `CONTAINS`/`IS` on fields named by its manifest. [TDH API](https://learn.microsoft.com/en-us/windows/win32/api/tdh/nf-tdh-tdhcreatepayloadfilter), [predicate operators](https://learn.microsoft.com/en-us/windows/win32/api/tdh/ns-tdh-payload_filter_predicate). **Inference:** a path predicate might reduce delivered ID 12/26/27/28/30 events if this kernel provider accepts it, but it cannot select the corresponding ID 15/16/17/18/19 events by path; filtering out nonmatching name events also breaks later joins. Microsoft documents the generic API, not a working `Kernel-File` path-scoped trace. Treat support and actual pre-delivery reduction as **unverified**, to be measured with all loss counters. No documented path filter scopes all its file operations to a root.

### Volume

No Microsoft source gives a fixed desktop event rate: it depends on workload, selected IDs/keywords, and background I/O. **Inference:** unfiltered read/write capture is whole-machine, so callback volume grows with every read/write, including caches, browser/profile activity, build tools and scans. The owner's **373,432 lost events** already rejects the prior Python/system-IO configuration for continuous scoring; the loss count is a floor on missing events, not the offered rate. For scale **only**, if that loss occurred over 5 seconds it would be at least 74,686 missing events/s; over 10 seconds, at least 37,343/s. Neither duration is a measured one. An 8,192-item application queue holds only 0.41 seconds at 20,000 callbacks/s if its consumer stalls. An event-ID filter could discard create/close/metadata categories, but cannot lower read/write volume below the number of selected read/write events. A path predicate on path-bearing events could reduce **those** events, but not their unnamed read/write companions. Thus the expected filtered volume is at least the selected system-wide read/write rate, which is **unknown on this desktop**. Do not claim a numeric filtered rate until measured; the target is zero ETW and queue loss in the owner's worst benign workload, with enough headroom for bursts. [Session loss fields](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/ns-evntrace-event_trace_properties).

## 2. Classic FileIo and the System IO provider

Microsoft says [System IO provider](https://learn.microsoft.com/en-us/windows/win32/etw/system-providers) maps `SYSTEM_IO_KW_FILE` and `SYSTEM_IO_KW_FILENAME` to the legacy FileIo/filename categories, requires `EVENT_TRACE_SYSTEM_LOGGER_MODE`, and still emits **system trace events**, not events bearing the new provider GUID. Its documented granularity is category keywords. The classic [FileIo ReadWrite](https://learn.microsoft.com/en-us/windows/win32/etw/fileio-readwrite) and [Name](https://learn.microsoft.com/en-us/windows/win32/etw/fileio-name) schemas are MOF/opcode based. The manifest event-ID filter cannot be assumed to match these classic opcodes, and the TDH payload-filter API specifically asks for a manifest provider/event descriptor. No Microsoft-documented PID, executable, or path filter for these system FileIo categories was found. **Inference:** absent a validated, provider-specific facility, assume no useful kernel-side actor/path scoping for either the legacy or new System IO surface. The new System IO GUID is an enablement wrapper for the same events, not a new lower-volume source. This confirms the owner's belief in the supported/documented sense; it is not a proof that undocumented mechanisms do not exist.

## 3. USN journal

NTFS [change journal records](https://learn.microsoft.com/en-us/windows/win32/fileio/change-journal-records) give a per-volume sequence of changed **objects**, not reads, write bytes, or a reversible history. [USN_RECORD_V2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/d2a2b53e-bf78-4ef3-90c7-21b918fab304) includes file/parent reference numbers, USN, timestamp, reason flags, and leaf name, **no PID or image**. Reasons include data overwrite/extend/truncate, create/delete, rename old/new, and close; flags can accumulate and multiple modifications coalesce. Path resolution by file ID may fail after delete or rename. `FSCTL_READ_USN_JOURNAL` can read at the tail or wait according to `BytesToWaitFor`/`Timeout`; latency is therefore configuration and workload dependent, not a Windows fixed delay. [Read parameters](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-read_usn_journal_data_v0).

The existing `usn.py` asks for `ReturnOnlyOnClose=1`, suppresses deleted records, and queues changed paths for scanning. `observers.py` ticks every 5 seconds and may defer an offered path until quiet (up to 60 seconds). **Inference:** that is suitable for catch-up and change-rate alerts, not a timely, complete 10-second writer-specific burst score. A separate owner-root USN observation would need reason/timestamp/rename preservation and lower latency, without disturbing the existing scanner cursor; it still could only produce **unattributed folder/file change rates**. Joining a USN record to a nearby ETW process event by timestamp or PID lifetime is **not attribution**: process events show lifecycle, not file access. A join is credible only when a loss-free operation event supplies matching file identity, process identity, and timing; USN can then corroborate that a change occurred. On ambiguity or ETW loss, abstain from per-process action.

Do not change Defender settings. |
| `ReadDirectoryChangesW` | [Directory/subtree notifications](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw) can provide fairly prompt names and action types for selected roots, with buffer-overflow recovery. The notification record has no writer PID or file content; use USN to reconcile loss. **Inference:** useful for owner-root aggregate alerts, not process suspension. |

Those settings are outside this round's constraints and broad auditing can be noisy. It is not an always-on source. |

## 5. Recommendation and owner-machine decision gate

**Recommendation:** keep process-only ETW and existing USN scanning in production for now. Use USN and, if needed, directory notifications for **unattributed, notify-only** document-change bursts. Treat CFA events as optional corroboration when they already exist. Do not feed guessed USN→process matches into `burst.Operation(attributed=True)` or turn a provisional ETW request into a confirmed change. **Inference:** the only plausible path to per-process read/write/rename/delete scoring under these constraints is a separately measured `Microsoft-Windows-Kernel-File` manifest session with event-ID/keyword selection and file-object/name joins; its viability is unknown, and a path payload filter alone cannot solve read/write volume.

First, on the owner machine **with explicit owner-run measurement rather than the installed service**, capture the installed provider's IDs/versions/keywords and whether enabling it in a private real-time session succeeds without altering another session. For short, bounded benign windows (idle, browser, document editing, backup/sync, build/scan, and a harmless disposable-document burst), compare: (1) name/create/path-only IDs; (2) selected read/write plus the minimum join events; (3) event-ID filter on/off; (4) a path payload predicate on a path-bearing ID **only if accepted**. Record generated/delivered counts by ID and keyword, callbacks/s average/peak, `EventsLost`, `RealTimeBuffersLost`, application drops/high-water, CPU/memory, timestamp-to-callback p50/p99/max, `FileObject`/`FileKey` join success, PID/creation-time match, and share of owner documents with complete read→change chains. Compare the peak to the current 20,000/s sustained guard and 8,192 queue. **Inference:** if representative windows show any loss, excessive latency, or low join coverage, retain unattributed notify-only scoring; a clean short run is only a feasibility signal, not a continuous-coverage guarantee. No numeric event-volume reduction from a manifest filter is promised before this measurement.
